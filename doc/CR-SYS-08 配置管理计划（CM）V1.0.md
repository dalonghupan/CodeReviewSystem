文档编号：CR-SYS-CM-V1.0

密级：内部受控文件
编制日期：2026-07-30

## 1 总则
### 1.1 编制目的
建立项目统一配置管理体系，对**代码源码、过程文档、软件版本、环境配置、基线制品**进行标识、受控入库、版本追踪、变更管控、发布回溯与归档管理；杜绝文档版本混乱、代码随意修改、配置泄露、基线丢失等问题，满足CMMI配置审计要求，实现所有配置项可追溯、可回滚、可审计。
### 1.2 配置管理适用范围
项目全生命周期所有产出物：需求/设计/计划类文档、前后端源代码、数据库脚本、Protobuf接口文件、K8s部署配置、中间件参数、测试用例与报告、镜像版本、基线发布单据、运维脚本；覆盖开发、测试、预发布、生产四大环境配置管控。
### 1.3 配置管理角色与整体原则
1. 基线先行：正式基线必须经过评审审批，纳入受控库，禁止使用非正式基线开展后续工作；
2. 变更受控：所有配置项修改必须走变更申请、评审、更新版本、记录日志；
3. 环境隔离：开发、测试、预发、生产配置文件相互独立，严禁跨环境混用配置；
4. 权限最小化：配置库读写权限分级分配，密钥类配置仅授权运维负责人查看；
5. 定期审计：配置管理员周期性执行配置审计，核对配置项完整性、一致性。

## 3 配置库划分与存储载体
整体划分**三大类配置库**，分别对应不同用途，使用Git代码仓库+共享文档仓库+制品仓库组合实现：
### 3.1 开发受控代码库（Git仓库）
1. 载体：企业内部私有Git仓库，开启权限分组、提交日志全程记录
2. 存放内容：6个微服务Go源码、Next.js前端源码、单元测试代码、Dockerfile、编译打包脚本、Protobuf定义文件、数据库DDL/DML脚本
3. 分支管理规范（强制GitFlow）
- `main`主干分支：存放所有正式基线版本，禁止直接推送代码，仅允许合并经过本系统代码评审完成的MR
- `develop`开发分支：日常迭代汇总分支，每日开发合入分支
- `feature/*`特性分支：开发人员单人功能开发分支，开发完成提MR至develop
- `hotfix/*`紧急修复分支：线上故障临时修复分支，修复后同步合并main与develop
- `release/*`发布分支：对应每一轮测试、上线版本，用于版本冻结打包
4. 代码提交约束：提交备注必须写明功能编号/缺陷编号；禁止无备注随意提交；合并MR必须完成系统内代码评审才可放行。

### 3.2 文档受控库（共享文档受控仓库）
1. 存放所有过程正式文档，包含版本号、审批签字记录：SRS、HLD、LLD、PDP、SQA、TP、本CM计划、各类评审记录、变更申请单、验收单据、质量报告、结项报告
2. 文档版本命名规则：`文档编号_主版本.次版本.修订号`，例如CR-SYS-SQA-V1.0、CR-SYS-SQA-V1.1，每次变更递增修订号；旧版本文档不得删除，做归档留存标记。

### 3.3 软件制品&环境配置库
1. 容器镜像仓库：存储各环境编译后的Docker镜像，镜像标签与release分支版本号一一对应，生产镜像打上唯一Release正式标签，不允许覆盖改写；
2. K8s配置仓库：独立Git仓库存放所有环境yaml部署文件、ConfigMap配置、中间件部署脚本，Secret敏感密钥统一交由K8s密钥管理系统托管，不存入代码与配置仓库；
3. 测试制品库：测试用例、缺陷台账、性能安全测试原始日志文件，统一打包归档存储。

## 4 配置项识别与分类清单

### 4.2 代码类配置项（Git源码库）

### 4.3 环境与部署配置项（K8s配置仓库+镜像仓库）

### 4.4 测试类配置项（测试制品库）
测试用例集、缺陷记录表、性能压测脚本、安全扫描脚本、各轮测试报告

## 5 基线管理（核心配置管理动作，CMMI强制要求）
### 5.1 四大核心正式基线，基线一经发布冻结，变更必须走正式变更流程
1. **需求基线**：SRS文档评审签字完成，文档库正式入库锁定
2. **设计基线**：HLD、LLD、接口定义、数据表脚本评审通过后锁定发布
3. **测试基线**：系统测试完成，P0/P1缺陷清零，对应release版本镜像冻结形成测试基线
4. **生产发布基线**：UAT验收通过，正式上线镜像、生产配置文件统一锁定归档，形成最终上线基线

### 5.2 基线创建流程
1. 对应阶段产出物全部完成内部评审；
2. 配置管理员核对全部配套配置项齐全、版本统一；
3. 项目负责人审批基线发布单；
4. 受控库标记基线版本号，打上基线标签，禁止未经变更流程随意修改基线内配置项；
5. 基线信息录入《基线管理台账》，台账永久归档。

## 6 配置变更管理流程
基线发布后，任何配置项修改均属于配置变更，分为**一般变更**、**重大变更**两类：
### 6.1 变更分级定义
1. 重大变更：需求基线改动、架构设计调整、数据表结构大幅修改、生产环境核心参数变更、主干版本迭代升级；需要项目经理+架构师双审批
2. 一般变更：页面文案调整、简单配置参数微调、测试用例补充、轻微BUG代码修复；配置管理员审批即可

### 6.2 标准变更五步流程
1. 变更申请人提交《配置变更申请表》，写明变更内容、变更原因、影响范围、预估工时、涉及配置项编号；
2. 对应级别负责人审批是否允许变更；重大变更额外组织评审会议评估风险；
3. 审批通过后，申请人修改对应配置项，同步更新版本号，填写变更日志；
4. 配置管理员核验修改内容与申请一致，更新受控库版本；涉及基线的同步更新基线版本并重新标记；
5. 变更完成闭环，变更申请表随配置项一同归档，写入配置变更台账。

### 6.3 禁止行为
无申请私自修改基线代码、私自改动生产配置、线下传输非正式版本文件，一经发现判定为配置严重违规，由SQA记录质量问题并限期整改。

## 7 版本控制与发布追溯管理
1. 源码版本：release分支版本号 = 镜像Tag版本号 = 文档配套版本号，三者保持强一致，做到输入一份版本号，即可查出对应代码、配置、文档全套制品；
2. 每一次测试发布、生产灰度发布，运维必须向CM管理员报备本次使用镜像版本、配置版本，登记进发布版本台账；
3. 版本回滚机制：镜像仓库永久保留历史正式版本镜像，配置仓库留存历史yaml配置，线上出现故障可依据基线版本一键回滚至上一个稳定基线版本；回滚操作同样需要填写配置变更备案。

## 8 配置备份与恢复策略
### 8.1 备份范围
Git所有仓库全量备份、受控文档库打包备份、K8s所有非密钥配置文件备份、镜像仓库关键生产镜像异地备份
### 8.2 备份周期
1. 代码&配置仓库：每日凌晨自动增量备份，每周一次全量异地备份；
2. 正式基线版本：基线发布完成立即手动额外独立备份一份，离线归档；
### 8.3 恢复要求
出现配置文件丢失、仓库误删、版本覆盖异常时，CM管理员依据备份记录完成恢复，恢复后核对配置项版本与基线一致性，生成恢复记录文档留存。

## 9 配置审计管理（CMMI强制审计项）
分为**日常小规模审计**、**里程碑正式配置审计**两种
### 9.1 日常审计（CM管理员每周执行）
1. 检查代码分支提交是否符合GitFlow规范，MR是否完成系统代码评审；
2. 核对正在使用的测试/预发版本配置是否与当前基线版本匹配；
3. 检查配置变更是否全部走完申请审批流程，无隐性修改；
### 9.2 里程碑审计（四大基线发布前必做正式审计，SQA参与）
1. 清点当前阶段所有必须交付的配置项是否齐全，无缺失文档、脚本；
2. 比对代码版本、部署配置版本、文档版本三者基线号统一；
3. 抽查密钥配置是否存在明文硬编码泄露风险；
4. 出具《配置审计报告》，审计不合格不得发布对应基线，整改后重新审计。

## 10 权限安全管控细则
1. 源码仓库：开发人员仅拥有自身feature分支推送权限，main分支仅CM与架构师拥有合并权限；
2. 文档受控库：普通开发只读，仅文档编制人与CM管理员可编辑修订；
3. K8s Secret密钥配置：仅运维负责人、CM管理员可查看导出，其余人员不可查看明文；
4. 生产环境配置文件：禁止开发人员直接登录生产节点修改任何配置，所有修改必须通过配置仓库提交变更后由运维统一下发生效；
5. 离职人员即时回收所有配置库、代码仓库权限，CM管理员更新权限台账。

## 11 配置管理风险与应对措施
| 风险描述 | 风险等级 | 应对处置方案 |
| ---- | ---- | ---- |
| 多人员并行修改同一文档/配置，出现版本覆盖冲突 | 中风险 | 文档采用在线锁定编辑模式，代码分支隔离开发，合并冲突必须人工核验解决并记录冲突说明 |
| 测试环境私自替换非正式镜像版本，与基线不符 | 中风险 | 每次部署前CM核对镜像Tag与基线版本号，版本不一致拒绝部署，SQA随机抽查核对 |
| 正式基线文档丢失、旧版本无法找回 | 高风险 | 基线发布立刻离线异地备份，禁止删除受控库任何历史版本文档，仅做作废标记 |
| 生产配置线下临时修改，未同步提交配置仓库，后续版本覆盖丢失改动 | 极高风险 | 生产所有配置只能由配置仓库下发，封闭节点本地修改权限，运维每轮发布校验本地配置与仓库一致性 |
